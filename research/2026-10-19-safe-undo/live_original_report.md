# Undo after later edits: six rules, an information limit, and production website tests

Date: October 19, 2026. Status: research note; required checks are recorded in the package. No human or peer review.

## Abstract

An agent can complete an action and later need to undo it. Restoring old values can remove later work. Applying an inverse can also be wrong if a later assignment has already removed the original effect. We compare six fixed undo rules on 15,624 synthetic histories, with 93,744 rule outcomes. The reference removes one agent increment and replays the same later commands. At the planned length-three setting, Value guard makes 96 false completion claims in 500 histories. Revision guard has no false claims but completes only four times. An ideal control with complete operation-type history completes correctly in all histories. A one-command pair has equal current values and revision counts but different correct undo targets. These are exact results for the stated model, not measured agent error rates. A separate production website extension assigns 48 core tests in Google Calendar and Notion. It has 43 valid results: 26 clean completions, 11 false confirmations and six abstentions. Five tests remain unknown. The history-informed control completes correctly in all seven valid cases; its eighth case is unknown. These selected tests do not estimate production error rates.

## Research question and safety relevance

Which undo rules remove one completed agent increment while preserving later fixed commands? Can field values and revision counts alone establish the right final state?

An **undo rule** attempts to remove an earlier effect. A **counterfactual target** is the result of a specified alternative execution. Here, the alternative omits the agent increment but keeps every later command and its order fixed. A **revision** counts writes to a field. **Provenance** records which operations still contribute to the current result. An **atomic event** completes without an intervening operation.

This question matters when an agent edits shared records and then cancels or repairs its work. An incorrect undo can damage work that occurred later. A successful write is not proof that the chosen undo was correct. We test prescribed controller rules, not a model's ability to choose or follow them.

The [October 17 report](../2026-10-17-repair-dependencies/report.md) tested forward repair decisions under concurrent edits. The [October 18 report](../2026-10-18-retry-retention/report.md) tested duplicate effects when request memory expires. This report tests removal of an earlier effect after later fixed commands. The production website extension below adds new undo tests. It does not change earlier retry or repair results.

## Related work and contribution

Korth, Levy and Silberschatz already compare compensation with histories that omit a canceled transaction. They give sufficient commuting-operation conditions and describe correction according to which transactions changed each entity. They also discuss the difficulty caused by changes in later program behavior. Our reference target and history-aware control follow this established direction. [Korth et al., 1990, selected sections recorded in the source log](https://www.vldb.org/conf/1990/P095.PDF)

Microsoft's current compensation guidance warns that old-state restoration can overwrite concurrent work. It states that compensation depends on application rules and need not return the system to its original state. Our model tests one atomic undo; it does not test a distributed recovery workflow or retry mechanism. [Microsoft, *Compensating Transaction pattern*](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)

Planarian records prior row data and affected keys for supported SQL operations and applies undo actions in reverse order. Its proxy locks and tenant-isolation assumptions matter. Our added later writers do not test or refute that implementation. LogAct uses shared action history for recovery and discusses limits on semantic recovery and external concurrency. SagaLLM records operations and dependencies for compensation. These cited versions are preprints; we use only the sections listed in the source record and do not reuse their benchmark results. [Guo et al., 2026](https://arxiv.org/html/2609.35366v1), [Balakrishnan et al., 2026](https://arxiv.org/html/2604.07988v1), [Chang and Geng, 2025](https://arxiv.org/html/2503.11951v3)

Zeng, Wu and Krishnan study removal of transactions generated by LLMs, using dependency information and buffering to preserve database constraints. Their preprint distinguishes preservation of constraints from exact equality of states. We test exact fixed-command equality and impose no database constraint. We do not reproduce that system. [Zeng et al., 2024](https://arxiv.org/html/2412.12493v1)

The contribution is the complete six-rule corpus, exact refusal accounting, minimum failure examples, and groups of equal observations with unequal required targets. No new compensation algorithm, target definition, general impossibility theorem, or novelty priority is claimed. A limited search cannot establish global novelty. The [source record](source_search.md) gives queries, dates, read scopes, metadata corrections and excluded leads.

## Method

The [plan](analysis_plan.md), [configuration](config.json) and [manifest](input_manifest.json) were saved before implementation and enumeration. The freeze time was 2026-10-19T14:30:22.004489+00:00. No frozen input changed. This is a local plan record, not an external preregistration.

The record has integer x and bit y. Each starts at 0 or 1. The agent adds 1 to x successfully. The background then executes every possible word of length zero through five over five commands: add1, sub1, set0, set1 and flip_y. The first four write x. The last flips y. Every x write increases its revision, including a set to the current value.

The reference executes the identical word from the initial record without the agent action. This fixes later commands and their parameters. It does not estimate how other actors would behave in a different world. There are no conditional branches, copied values, arithmetic bounds, external effects, permission changes or multi-record constraints. These exclusions are necessary for the result.

After the word, one undo rule runs once. Its observation, condition and write are atomic. There is no intervening write, lost reply, crash or retry. Each rule receives a fresh copy of the same history. The evaluator can inspect the reference target; the rules cannot.

| Rule | Action and completion condition |
| --- | --- |
| Full restore | Restore both initial fields. Always report complete. |
| Field restore | Restore initial x and preserve current y. Always report complete. |
| Subtract | Subtract 1 from current x. Always report complete. |
| Value guard | Restore initial x only if current x equals initial x+1. Otherwise abstain. |
| Revision guard | Restore initial x only if no later x write occurred. Otherwise abstain. |
| Provenance control | Subtract 1 only if no set command occurred. Otherwise make no change. Report complete. |

All rules except Full restore preserve current y. Provenance control receives a trusted bit that starts true and becomes false at the first set. This stronger information is intentional. A normal browser field read does not provide it. Revision guard assumes a complete, non-reused x revision. It allows independent y changes.

At length L there are 4*5^L histories. Enumeration includes every history once. It uses no sampling, training, tuning or random seed. Equal enumeration weights are not a claim about natural frequencies. The planned primary table uses L=3.

## Measures and decisions

A correct final record equals the reference target in both fields. A false confirmation reports complete with a wrong record. A wrong change changes the record and leaves a wrong result. A collateral change changes y during undo. New damage starts from a correct pre-undo record and makes it wrong. An unresolved case abstains with a wrong record. An abstain-correct case abstains with a correct record. A clean completion reports complete with a correct record.

Clean completion, false confirmation, unresolved and abstain-correct form four separate outcome groups. Other labels overlap. For example, new damage can also be a false confirmation and a wrong change.

The six frozen hypotheses test restoration failures, the boundary of subtraction, value-check failures, conservative revision safety, the ideal history control, and unequal targets under equal observations. All six pass. A failed hypothesis would have remained in the report. Exact finite counts do not require sampling confidence intervals or p-values. Generalization remains unmeasured.

Value guard reports complete in 124 cases; 96 are wrong. Each of those 96 cases was already correct before undo. The unchanged value did not establish that the agent increment still contributed to it. Revision guard avoids wrong changes and claims, but abstains in 496 cases. Of these, 392 already equal the reference and 104 retain the agent effect. These are paired costs under a fixed target, not measured delays or general failure rates.

Across all lengths, Subtract has 14,168 false confirmations and new-damage cases. These are exactly the histories that include a set. It completes correctly in all 1,456 no-set histories. Revision guard completes correctly in 24 cases, abstains with a correct record in 14,168, and leaves 1,432 unresolved. Provenance control completes correctly in all 15,624 histories.

### A one-command false confirmation

Start at (x,y)=(0,0). The agent adds 1, so x becomes 1. A later actor executes set1. The value remains 1, but the later assignment also makes the reference target 1. Value guard sees the expected value and restores x to 0. It reports complete and creates a wrong result. Revision guard sees one later x write and abstains. Provenance control records that the assignment removed the original contribution and leaves x at 1.

This is a deliberately defined assignment with known meaning. It does not establish that all same-value writes in real systems transfer ownership or erase every earlier effect.

### Equal observations, different correct targets

Start again at (0,0), then add the agent increment. Compare a later sub1 with a later set0. Both leave the actual record at (0,0), with one x write. Their history length and initial values also match. Without the agent increment, sub1 would leave (-1,0), while set0 would leave (0,0).

Thus a rule with only those observations cannot always select a correct final record for both histories. It can abstain or obtain more operation information. This limit does not apply to the history-aware control. The pair is minimum under the frozen order and occurs at length one.

The full grouping includes 364 observation groups. Of these, 140 have different reference targets. They contain 8,288 histories. At L=3 there are 24 ambiguous groups containing 272 of the 500 histories. Full group membership counts and minimum pairs are in [observation_groups.json](observation_groups.json). These counts depend on the selected alphabet and observation set.

## Why the controls work

After the agent increment, actual x minus reference x equals 1. Additions, subtractions and y flips preserve that difference. A set makes it zero, and later commands keep it zero. The trusted provenance bit tells the control whether subtraction is required. If no x write occurred, restoring initial x is also safe; this is the case accepted by Revision guard.

The [derivations](derivations.md) give the full argument, the equal-observation proof and count identities. They also show that Full restore has 4*(5^L-3^L)/2 collateral cases. All six rules pass the four no-background controls. Weak rules are therefore not wrong in every setting.

## Production website extension

### Live question and plan

The user requested tests in connected production accounts. We therefore added a separate case series in Google Calendar and Notion on October 19. A **case series** is a set of selected tests; it is not a random sample of all use. This extension tests whether prescribed undo decisions produce the specified saved state. It does not test whether a model can discover the right rule.

The [live plan](live_plan.md), [assignments](live_assignments.json), [rule code](live_rules.js), and [instructions](live_runner_instructions.md) were frozen at 2026-10-19T14:54:32.433607+00:00. The [manifest](live_input_manifest.json) records their hashes. Two unscored interface checks preceded the freeze. They tested saved fields, stable record identity and recoverable deletion. Notion initially showed an old value after a save. The frozen procedure closes the editor, waits two seconds, reloads, waits two seconds, and then reads the saved fields. This is a test-specific procedure, not a provider guarantee.

The design assigns four histories to each of six rules on each site: 48 core assignments. Four further diagnostic histories have no undo. Each valid trial uses a fresh temporary record. The order was shuffled with seed 2026101901 and saved before execution. This order does not make the cases a population sample. No replacement trial is allowed.

### Live fields and rules

Calendar X is a plain integer in Description. Y is availability: Free=0 and Busy=1. Each test event is private, all day on October 14, 2026, without guests, reminders, location, conference or recurrence. Notion uses a new private database with X as Number and Y as Checkbox. Name holds a unique test marker. The page body stays empty. Only temporary records change. All mutations use the browser interface.

Each test starts at (0,0). The agent sets X=1. The later phase either does nothing, flips Y, adds 1 to X, or saves X=0 and then X=1. The last case has two separate saved changes. It avoids an unsupported assumption that saving an unchanged value always creates a write. For valid trials, each phase and the final result are read after reload on the same native record identity. Arithmetic uses a read, a calculation and a literal field save.

The first four rules use current fields. The **Log-assisted revision guard** also receives the verified test log of later X writes. The **Log-assisted provenance control** receives the command types in that log. These are stronger inputs. Neither rule reads a native field revision counter or infers intent from the website. Google documents resource-level ETags and conditional API changes; this does not show that a browser Save uses a field guard. Notion documents a page edit time, not a complete X-write count. [Google](https://developers.google.com/workspace/calendar/api/guides/version-resources), [Notion](https://developers.notion.com/reference/page)

The browser agent records the fixed rule output before it acts. Here, a false confirmation means that the fixed rule says complete but the saved result is wrong. It does not mean that a new success message was sent to the user. The evaluator computes the reference separately by omitting the agent action and applying the prescribed later commands to (0,0). Later edits are controlled phases by the test driver. They are not natural user activity. There is no deliberate outside writer during the read-to-write interval. Thus the test does not validate atomicity or race safety.

## Discussion

Undo needs a target that states which later effects to preserve. Old values alone do not define that target. An inverse is safe only under suitable operation semantics. A set can make the original contribution absent, so an additional inverse creates a new error.

Revision-based refusal can prevent damage, but refusal and successful undo are different outcomes. An evaluation that counts only wrong writes can hide unresolved work. Our four-way outcome split keeps these cases visible. The history control illustrates what additional information can resolve in this model; it does not show that a website exposes that information reliably.

## Limitations

The exhaustive result is a simulation of fixed rules. The separate live extension tests prescribed browser actions in two production accounts. The alphabet, initial states and maximum length are small. The proof covers longer words only under the same operation semantics. Counts are not estimates of production risk.

The reference fixes later commands. Real actors can read intermediate values, select different branches, copy data, or produce external effects. Removing the earlier action can change those later decisions. Our exact target then need not describe a meaningful real undo.

The model assumes fresh observations, complete write counts, trusted operation-type records and atomic undo. It omits record identity errors, access revocation, crashes, retries, non-atomic updates, overflow and application constraints. Provenance control has more information than the baselines. This is not a fair-information model benchmark or a claim that simple provenance is sufficient for arbitrary state.

There was no human review or external peer review. The source search is limited, and no priority claim is made.

## Ethical and misuse considerations

All test values are synthetic. The live extension uses temporary records in connected accounts. Public extracts omit native record IDs, account details and unrelated interface content. Full private action logs and screenshots stay local. No paid compute or new paid API service was used. No third-party code or dataset was copied, and no new license is assigned to the repository owner's work. Source attribution and read scope are retained.

These results do not authorize automatic rollback of real user work. A system needs a defined recovery contract, suitable permissions and evidence that its checks cover the actual effect. This report contains no instructions for harmful access or interference with other users.
